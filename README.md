# confcli — CLI-утилита для Confluence

`confcli` — инструмент командной строки для работы с Atlassian Confluence Private Server. Позволяет получать, искать, создавать и редактировать страницы Confluence прямо из терминала. Кроссплатформенный, поддерживает множество форматов вывода, экспорт целых пространств и интеграцию с LLM-агентами.

## Установка

### Через Go

```bash
go install confcli@latest
```

### Сборка из исходников

```bash
git clone <url-репозитория>
cd confcli/confcli-bin
go build -o confcli ./cmd/confcli
```

### Установка в PATH

После сборки или скачивания бинарника:

```bash
# Установит симлинк в /usr/local/bin (может потребовать sudo)
confcli install

# Установка в произвольную директорию
confcli install --dir ~/bin

# Копирование бинарника вместо симлинка
confcli install --copy
```

### Обновление

```bash
# Проверить наличие обновлений
confcli update --check

# Обновить до последней версии
confcli update
```

## Конфигурация

### Быстрая настройка

```bash
confcli config init
confcli config set url https://confluence.example.com
confcli config set token ваш-api-токен
confcli config set username user@example.com
```

### Профили

Конфигурация хранится в `~/.confcli/config.yaml` и поддерживает несколько профилей:

```yaml
current_profile: default
profiles:
  default:
    url: "https://confluence.example.com"
    token: "ваш-api-токен"
    username: "user@example.com"
    auth_type: "bearer"
    read_only: false
  prod:
    url: "https://confluence-prod.example.com"
    token: "prod-токен"
    username: "admin@example.com"
    auth_type: "bearer"
    read_only: true
```

Поле `read_only: true` запрещает любые операции записи для профиля.

### Открытие страницы логина

```bash
confcli login
```

Откроет страницу логина Confluence в браузере по умолчанию.

## Основные команды

### Получение страниц

```bash
# По ID
confcli page get --id 123456

# По пространству и заголовку
confcli page get --space DEV --title "Архитектура проекта"

# По пути
confcli page get --path "DEV/Проект/Документация"

# Конкретная версия страницы
confcli page get --id 123456 --version 3

# С комментариями и метками
confcli page get --id 123456 --with-comments --with-labels

# Со всеми потомками (требует --format json)
confcli page get --id 123456 --with-descendants --format json
```

### Создание, обновление, удаление страниц

```bash
# Создание страницы
confcli page create --space DEV --title "Новая страница" --content-file content.md --confirm

# Создание дочерней страницы
confcli page create --space DEV --title "Подстраница" --parent 123456 --content-file body.md --confirm

# Обновление страницы
confcli page update 123456 --content-file updated.md --version-comment "Обновление" --confirm

# Удаление страницы
confcli page delete 123456 --confirm
```

Все операции записи требуют флаг `--confirm`.

### Поиск

```bash
# Простой поиск
confcli search "документация API"

# Поиск по CQL
confcli search --cql 'space = "DEV" AND text ~ "performance"' --limit 20

# Поиск в конкретном пространстве
confcli search "логирование" --space DEV
```

### Комментарии и метки

```bash
# Список комментариев
confcli page comments 123456

# Добавить комментарий
confcli page comment add 123456 --text "Нужно обновить раздел" --confirm

# Список меток
confcli page labels 123456

# Добавить метку
confcli page label add 123456 --label "важное" --confirm
```

### Сравнение версий

```bash
# Diff двух версий страницы
confcli page diff 123456 --old-version 2 --new-version 5

# Diff в формате export (чище для markdown)
confcli page diff 123456 --old-version 1 --new-version 3 --format export

# Со статистикой изменений
confcli page diff 123456 --old-version 2 --new-version 5 --summary
```

## Иерархия и экспорт пространств

### Просмотр иерархии

```bash
# Дерево пространства
confcli hierarchy space --space DEV --tree

# Плоский список всех страниц
confcli hierarchy space --space DEV --flat --format json

# Дерево поддерева по page-id
confcli hierarchy space --space DEV --page-id 123456 --tree

# Ограничение глубины
confcli hierarchy space --space DEV --depth 2 --tree
```

### Экспорт пространства на диск

```bash
# Экспорт всего пространства в директорию
confcli hierarchy space --space DEV --output-dir ./export

# Экспорт поддерева конкретной страницы
confcli hierarchy space --space DEV --page-id 123456 --output-dir ./export

# Экспорт версий страниц на определённую дату
confcli hierarchy space --space DEV --output-dir ./export --date 2024-06-15

# Экспорт в формате storage (сырой HTML)
confcli hierarchy space --space DEV --output-dir ./export --format storage
```

При экспорте отображается прогресс-бар для отслеживания хода загрузки. Ошибки загрузки отдельных страниц выводятся в stderr, но не прерывают экспорт — оставшиеся страницы продолжают скачиваться.

`hierarchy space` выгружает страницы и ссылки на изображения/вложения. Самостоятельно скачивать все двоичные вложения, сохранять исходники Draw.io или создавать их PNG эта команда не умеет. Для автономного дерева Git нужен отдельный шаг: получить список вложений страницы через `/rest/api/content/{id}/child/attachment`, скачать нужные файлы по `_links.download` и заменить ссылки в Markdown на локальные. У вложения может быть другая страница-владелец, например при Include. При переносе опубликованной диаграммы выбирайте редакции исходника и PNG, которые использует страница: последняя редакция вложения может отличаться. Сохраняйте размер, версию и SHA256 скачанных файлов для сверки.

### Scroll Versions

Если пространство использует плагин Scroll Versions, confcli автоматически обнаружит доступные версии и выведет их список. Для экспорта конкретной версии:

```bash
# Экспорт конкретной версии
confcli hierarchy space --space DEV --output-dir ./export --scroll-version "Release 2.0"
```

### Флаги экспорта

| Флаг | Описание |
|------|----------|
| `--named-folders` | Использовать транслитерированные имена страниц для папок вместо ID |
| `--clean-names` | Заголовки страниц как имена файлов/папок: убираются запрещённые символы, точки и пробелы заменяются на `_` |
| `--flat-leaves` | Не создавать подкаталог для страниц без потомков — файл сохраняется прямо в родительскую папку |
| `--rewrite-links` | Перезаписать внутренние ссылки Confluence на относительные пути файлов (по умолчанию включено) |
| `--rewrite-tfs-links` | Перезаписать ссылки TFS/Git-репозиториев на локальные пути |
| `--save-metadata` | Сохранять `.meta.json` для каждой страницы и `_space_metadata.json` для пространства |
| `--skip-root` | Пропустить корневую страницу — дочерние страницы экспортируются прямо в output-директорию |
| `--no-toc` | Удалить оглавление из экспортированного markdown |
| `--no-length-limit` | Снять ограничение в 80 символов на длину имён файлов и папок |
| `--date` | Получить версии страниц, актуальные на указанную дату (формат: `YYYY-MM-DD` или RFC3339) |
| `--transform` | Применить профиль трансформации (имя профиля или путь к YAML-файлу) |
| `--set` | Переопределить параметры профиля трансформации (например, `--set page.format=html`) |
| `--scroll-version` | Экспортировать конкретную версию Scroll Versions (требуется плагин Scroll Versions) |

## Загрузка markdown-дерева в Confluence (`confcli sync`)

Команда `confcli sync` синхронизирует локальное дерево markdown-файлов с деревом страниц Confluence — это обратное направление к `hierarchy space`. Поведением управляет **импорт-профиль** (`kind: import`) в `~/.confcli/transformations/`.

Каждая загруженная страница помечается лейблами `confcli-id-<sha>` (привязка к исходному файлу) и `confcli-hash-<sha>` (хеш контента), что позволяет последующим запускам определить, какие страницы создать, обновить, пропустить или пометить как «осиротевшие» (orphan — больше нет исходного файла).

```bash
# Сухой прогон: построить и распечатать план, ничего не применяя
confcli --read-only sync --profile docs --from ./docs --space TEST --root 12345 --dry-run

# Загрузить дерево в тестовое пространство после проверки плана
confcli sync --profile docs --from ./docs --space TEST --root 12345
```

### Флаги

| Флаг | Описание |
|------|----------|
| `--profile` | Имя или путь импорт-профиля (обязательно) |
| `--from` | Локальная директория с markdown-файлами (обязательно) |
| `--space` | Ключ пространства Confluence (обязательно) |
| `--root` | ID корневой страницы Confluence (обязательно) |
| `--dry-run` | Построить и распечатать план, не применяя изменения |
| `--file` | Точный путь одного Markdown-файла относительно `--from`; остальные страницы не записываются |
| `--file-list` | UTF-8 файл с точными путями Markdown относительно `--from`, по одному на строку; только выбранные страницы записываются последовательно |

Глобальный флаг `--read-only` неявно включает `--dry-run`.

`--file` и `--file-list` нельзя использовать вместе. Список не поддерживает glob-шаблоны; пустой список, повторный путь, два пути к одной странице или отсутствующий родитель отклоняются до записи. Для списка сохраняются полная карта ссылок и исходный порядок плана; невыбранные родители остаются read-only. При ошибке страницы или вложения применение списка останавливается перед следующей страницей; уже выполненные действия остаются в отчёте.

Для поштучной загрузки сохраняйте `--from` на корне полного дерева и добавляйте `--file`, например `--file "requirements/Раздел/Документ.md"`. Карта ссылок строится по всему дереву; существующие родители остаются read-only, даже если их локальное содержимое изменено. Отсутствующего родителя нужно загрузить отдельным запуском прежде дочерней страницы. Путь должен обозначать включённый профилем файл; абсолютные пути, `..` и glob-шаблоны отвергаются до записи. Полный план сначала проверяется, затем ограничивается выбранной страницей; unselected страницы и orphan не применяются.

### Обновление одной существующей страницы

1. Сопоставьте файл с существующей страницей через `overrides.page_id`. Сохраните её исходный заголовок в `overrides.title`. Цель должна принадлежать выбранному пространству и дереву `--root`; профиль для личной копии и профиль для исходного пространства содержат разные ID.
2. Сравните актуальное содержимое Confluence с Git, включая таблицы, примеры и макросы. Сохраните текущую версию, body, родителя и вложения. `update` в плане не означает содержательного отличия: отсутствие или изменение метки `confcli-hash` тоже приводит к обновлению.
3. Выполните поштучный dry-run и проверьте целевой ID, заголовок, родителя, список вложений и ошибки. Записываемой страницей может быть только выбранный файл; `skip` для родителей нужен для разрешения иерархии. Ошибка в другом включённом файле может остановить построение общего плана.
4. Перед настоящим запуском повторно проверьте, что исходная страница и локальные файлы не изменились. Затем выполните ту же команду без `--read-only` и `--dry-run` в конфигурации с `read_only: false`. Отдельного флага `--apply` нет: каждый запуск заново строит план.
5. Проверьте результат и повторите dry-run: для неизменённых файла, профиля и вложений ожидается `skip`, без загрузки вложений. До применения в рабочем пространстве проверьте выбранную страницу в тестовой копии.

```powershell
confcli --read-only --format json sync --profile ./import.yaml --from ./docs --space TEST --root 12345 --file "requirements/Раздел/Документ.md" --dry-run
# После проверки плана и актуальности исходной страницы:
confcli sync --profile ./import.yaml --from ./docs --space TEST --root 12345 --file "requirements/Раздел/Документ.md"
```

`sync` заменяет body страницы целиком; автоматического слияния правок Git и Confluence нет. Успешный `update` создаёт следующую версию страницы, а прежние остаются в истории. `skip` и dry-run версию не создают. Родитель, служебные метки и вложения также могут измениться. Защиты от правок страницы между проверенным dry-run и следующим запуском сейчас нет; актуальность проверяется отдельно. Страницы `orphan` только перечисляются и автоматически не удаляются, поэтому удаление существующих страниц перед обновлением не требуется.

### Импорт-профиль

```yaml
kind: import

tree:
  folder_page: README.md      # файл-маркер: его контент становится родительской страницей папки
  # folder_page: "{dir}.md"   # альтернатива: одноимённый файл (docs/docs.md → страница «docs»)
  skip:
    - "**/node_modules/**"
    - "_drafts/**"
  flatten:                    # папки, не превращающиеся в собственную страницу — их дети поднимаются к родителю
    - "appendix/**"

  title:                      # как превращать имя файла в заголовок страницы Confluence
    rewrites:                 # применяются по порядку к stem-имени (без .md)
      - { pattern: "_",            replacement: " " }
      - { pattern: '^\d+[-_. ]+',  replacement: "" }    # снять «01-» / «03_» префиксы
      - { pattern: '\s+',          replacement: " " }
    trim: true

overrides:                    # доступные per-path переопределения (по doublestar-маске)
  - path: "draft/**"
    skip: true
  - path: "docs/onboarding.md"
    page_id: 12345            # пин к существующей странице, в обход поиска по id-лейблу
    title: "Onboarding"      # исходный заголовок выбранной страницы

plantuml:                     # ссылки на .puml/.plantuml → макрос Confluence (например, view-git-file)
  macro: view-git-file
  parameters:
    path: "{path}"
    branch: "refs/remotes/origin/{branch}"
    repository-id: "6"
    renderpuml: "true"

git_files:                    # catch-all: ссылки на не-md/не-puml файлы (yaml, json, sql, sh, ...)
  macro: view-git-file
  parameters:
    path: "{path}"
    branch: "refs/remotes/origin/{branch}"
    repository-id: "6"
  mode: link                  # link (по умолчанию) | inline
  per_extension:              # переопределение режима для конкретных расширений
    yaml: inline
    sql: inline
  inline:
    max_bytes: 200000         # файлы крупнее этого размера откатываются на link-режим
```

#### Заголовки страниц (`tree.title`)

`rewrites` — это упорядоченный список пар «regex → замена», применяемых к имени файла после удаления расширения `.md`. Поддерживаются ссылки на захваты (`$1`, `$2`). Преобразования влияют **только на заголовок страницы Confluence**; путь, по которому идёт привязка через `confcli-id-` лейбл и резолв forward-ссылок, не трогается. Это значит, что переименование заголовка в профиле не «теряет» уже загруженные страницы.

#### Режимы для не-markdown файлов (`git_files.mode`)

- **`link`** (по умолчанию) — ссылка оборачивается в макрос (обычно `view-git-file`), Confluence подтягивает содержимое из git при рендере страницы
- **`inline`** — файл читается из `--from` во время синхронизации и вставляется в страницу как Confluence-макрос `code` с подсветкой по расширению. Если файл недоступен, превышает `inline.max_bytes`, или выходит за пределы `--from`, происходит откат на `link`-режим (с предупреждением в stderr)
- **`url`** — обычная ссылка на файл в браузере TFS, с сохранением текста ссылки. Задайте `git_files.url` — URL репозитория вида `https://tfs.example.com/Collection/Project/_git/Repo`. Путь вычисляется относительно корня Git, параметры `path` и `version=GB<branch>` кодируются автоматически. Поддерживаются ссылки внутри таблиц и файлы без расширения; изображения `![alt](image.png)` обрабатываются отдельно.

Per-extension переопределения позволяют смешивать режимы — например, инлайнить yaml/sql, но оставлять ссылками pdf и большие дампы.

### Изображения, вложения и диаграммы при `sync`

Локальные изображения PNG/JPEG/GIF/SVG/WebP/BMP загружаются как вложения страницы; `![подпись](путь)` становится изображением Confluence. Обычная ссылка на такой файл становится ссылкой на скачивание. Пути разрешаются относительно Markdown-файла; в Git-репозитории можно ссылаться на файлы вне `--from`, если они остаются внутри репозитория. Внешние изображения остаются по исходным URL. Недоступное локальное изображение вызывает предупреждение; его нужно исправить до публикации.

Остальные локальные вложения выбираются по маскам `attachments.paths`. Загружаются только файлы, на которые ссылается выбранная страница, а не всё содержимое подходящих каталогов:

```yaml
attachments:
  paths: ["requirements/_attachments/**", "requirements/_diagrams/**"]
```

Здесь `--from` указывает на `docs`; при `--from docs/requirements` маски должны быть `_attachments/**` и `_diagrams/**`. Это могут быть PDF, офисные документы и редактируемые `.drawio`. Не включайте каталоги бэкапов широкими масками: ссылка на архивный `.md` иначе станет скачиваемым вложением вместо перехода на страницу. Отсутствующий явно выбранный файл останавливает построение плана. На одной странице имена вложений должны быть уникальными: два разных файла с одинаковым basename не сохраняются раздельно.

Байты вложений участвуют в хеше страницы. Ошибка загрузки вложения попадает в отчёт и не фиксирует успешный хеш: следующий `sync` повторяет попытку. Загрузка страницы и её вложений не является одной транзакцией; после ошибки body уже может быть обновлён. Повторная загрузка файла с тем же именем обновляет существующее вложение.

Для Draw.io локальная пара PNG + `.drawio` загружается как картинка и ссылка на редактируемый исходник, а не как автоматически восстановленный макрос Draw.io. Встроенный PlantUML загружается как макрос `plantuml`, ссылочный `.puml` — по секции `plantuml` профиля. Файлы для `view-git-file` и `git_files.mode: url` должны существовать в указанной опубликованной ветке Git. Проверка плана не подтверждает доступность файлов для плагина или внешний вид диаграммы. Предупреждения PlantUML о теме/CSS не исправляются автоматически при экспорте.

### Сохранение макросов при экспорте и обратной загрузке

Для `hierarchy space` задайте `page.preserve_macros: true` в экспорт-профиле или `--set page.preserve_macros=true`. Настройка работает с `markdown` и `export` и может переопределяться для отдельных страниц в `pages:`.

Экспорт использует `storage` для структуры документа и ссылок; в режиме `export` дополнительно использует HTML из `export_view` для макросов плагинов, если найдено совпадение `ac:macro-id` с `data-macro-id`. Если такого совпадения нет, макрос конвертируется из storage. Оба представления запрашиваются для одной версии страницы, в том числе при `--date`.

- Page Include превращается в `![Заголовок](относительный_путь.md)` на месте исходного макроса. При `sync` такой embed становится макросом `include`; `tree.include_page_macro: false` превращает его в обычную ссылку на страницу. По умолчанию Include включён.
- Expand сохраняет содержимое между `<!-- expand-start: Заголовок -->` и `<!-- expand-end -->`. Вложенные Expand и Panel поддерживаются; несколько параметров макроса сохраняются в комментарии как JSON.
- Anchor сохраняется как `<a id="имя-якоря"></a>`, а ссылки сохраняют `#имя-якоря`. При `sync` пустой элемент якоря восстанавливается в макрос `anchor`.
- Блоки `plantuml` и `puml` в Markdown загружаются как макрос `plantuml` с исходным текстом. Ссылки на `.puml` продолжают использовать настройки секции `plantuml` импорт-профиля.

Для чтения целых страниц включите `page.inline_transclusions: true`. Текст Include и Excerpt Include выгружается непосредственно в документ, на месте исходной вставки. Отдельные документы «фрагмент» или «включение» не создаются. Ссылки и картинки разрешаются в контексте настоящей страницы источника; вложенные вставки поддерживаются, циклы и превышение глубины 16 отвергаются. Отсутствующий источник и именованный Excerpt Include вызывают явную ошибку. Режим также работает в `page get` с профилем.

Невидимые комментарии `confcli-transclusion` сохраняют источник и контрольную сумму вставки. При `sync` с импорт-профилем неизменённый снимок восстанавливается в исходный живой макрос. Редактирование снимка останавливает загрузку: редактируйте страницу источника либо осознанно удалите обе границы, чтобы получить обычный текст на странице потребителя. Собственное содержимое Excerpt остаётся редактируемым. Отдельный перенос вложений или изменение локальных ссылок требует пересчёта контрольных сумм; снимок не заменяет сверку актуальности перед публикацией.

Сохраняйте комментарии параметров примеров кода: они возвращают заголовок и сворачивание в Confluence, включая примеры в таблицах. Для буквенной/римской нумерации экспорт может сохранять HTML-списки; их отображение в Git зависит от Markdown-просмотрщика. Локальные ссылки с жирной или курсивной подписью восстанавливаются как оформленные ссылки Confluence.

Таблицу, относящуюся к пункту списка, записывайте с отступом всех её строк внутри этого пункта. Экспорт и `sync` восстанавливают такой отступ у таблицы с начальным `|`, если перед ней стоит пункт списка, а после неё продолжается нумерованная последовательность. Получается один непрерывный список: Confluence может игнорировать начальный номер отдельного списка. Независимый список после таблицы отделяйте пустой строкой; инструмент сохраняет или добавляет этот разделитель, чтобы пункты не становились ячейками таблицы.

Для восстановления Expand/Panel добавьте в импорт-профиль:

```yaml
transforms:
  - type: restore_macro
```

`restore_macro` поддерживает `start_pattern`, `end_pattern`, `auto_params` и `macro_mapping`; полный пример находится в импорт-профиле ниже. Преобразования импорт-профиля выполняются до и после конвертации Markdown в storage. Неизвестное преобразование, неправильная вложенность или незакрытый маркер приводят к ошибке до применения плана синхронизации. Примеры внутри блоков кода и inline code сохраняются буквально.

Примеры профилей: [export-preserve-macros.yaml](confcli-bin/examples/export-preserve-macros.yaml) и [import-preserve-macros.yaml](confcli-bin/examples/import-preserve-macros.yaml). Первый сохраняет макросы и целые страницы с Include; второй использует локальные вложения, обычные ссылки TFS для файлов и `view-git-file` для ссылочных диаграмм. Настройте пространство, ID корней, сопоставление страниц, репозиторий и опубликованную ветку для своей среды.

```powershell
confcli --read-only hierarchy space --space SOURCE --page-id 12345 --transform ./confcli-bin/examples/export-preserve-macros.yaml --output-dir ./export --skip-root
confcli --read-only sync --profile ./confcli-bin/examples/import-preserve-macros.yaml --from ./export --space TEST --root 67890 --dry-run
```

Замените пространство и корневую страницу на нужные. Для переписывания ссылок на файлы TFS при экспорте дополнительно задайте `--rewrite-tfs-links`, `--tfs-base-url` и `--local-repo-path`.

## Профили трансформации

Профили трансформации позволяют задать набор правил обработки контента при экспорте: удаление макросов, замена ссылок, модификация текста и другие преобразования. Профили описываются в формате YAML.

### Использование

```bash
# Экспорт с профилем трансформации
confcli hierarchy space --space DEV --output-dir ./export --transform my-profile

# Профиль из файла
confcli hierarchy space --space DEV --output-dir ./export --transform ./custom-profile.yaml

# Переопределение параметров профиля
confcli hierarchy space --space DEV --output-dir ./export --transform my-profile --set page.format=html --set folder.flat_leaves=true

# Получение страницы с трансформацией
confcli page get --id 123456 --transform my-profile
```

### Управление профилями

```bash
# Список доступных профилей
confcli transform list

# Показать содержимое профиля
confcli transform show my-profile

# Создать шаблон профиля
confcli transform init my-profile

# Перезаписать существующий профиль
confcli transform init my-profile --force
```

Именованные профили хранятся в `~/.confcli/transformations/` как `.yaml`-файлы. Также можно указать путь к произвольному файлу.

### Формат профиля

```yaml
folder:
  naming: slug        # slug, title или id
  length_limit: 80    # максимальная длина имён папок (0 = без ограничений)
  flat_leaves: false   # сохранять конечные страницы прямо в родительскую папку

page:
  format: markdown     # markdown, storage, html, plain, export
  strip_toc: false     # удалить оглавление
  save_metadata: false # сохранять .meta.json

  transforms:          # конвейер трансформаций контента
    - type: remove_macro
      params:
        macro_names: [toc, status]
        # preserve_content: true  # сохранить содержимое макроса (например, для expand)

    - type: remove_element
      params:
        selectors: [".confluence-information-macro"]

    - type: modify_content
      params:
        phase: post    # pre (до конвертации) или post (после конвертации)
        rules:
          - find: "старый-текст"
            replace: "новый-текст"

    - type: modify_links
      params:
        rules:
          - find: "https://old-domain.com"
            replace: "https://new-domain.com"

    - type: rewrite_tfs_links
      params:
        tfs_base_url: "https://tfs.example.com"
        local_repo_path: "/path/to/repo"

    - type: rewrite_internal_links
      params:
        conf_base_url: "https://confluence.example.com"

pages:                 # переопределения для конкретных страниц
  - id: 12345
    strip_toc: true
  - path: "*/Archive/*"
    skip: true         # пропустить страницы, соответствующие шаблону
  - id: 67890
    flatten: true      # «глубокий flatten»: ВСЕ потомки этой страницы (включая внуков
                       # и далее) сохраняются прямо в её папку, без вложенной структуры
    skip_transforms: true  # не применять трансформации к этим страницам
```

#### Два режима «плоского» вывода

Есть две разные настройки, и их легко перепутать:

| Настройка | Где задаётся | На что влияет |
|-----------|--------------|---------------|
| `folder.flat_leaves: true` (или флаг `--flat-leaves`) | глобально для всего экспорта | Только **листовые** страницы (без потомков): их `.md`-файл сохраняется прямо в папке родителя, без отдельной подпапки. Промежуточные узлы по-прежнему получают свои папки. |
| `flatten: true` под `pages:` | для одной конкретной страницы (по `id` или `path`) | **Глубокий flatten**: вся ветка под этой страницей разворачивается в её папку — внуки, правнуки и т.д. оказываются на одном уровне, как сиблинги, без вложенных папок. |

Пример: пусть у страницы `API` есть подстраницы → подподстраницы (диаграммы, таблицы и т.д.), а ветка `Руководство` сохраняет вложенную структуру:

```yaml
folder:
  flat_leaves: false
pages:
  - id: 583906564          # страница «API»
    flatten: true
```

Результат: всё содержимое поддерева `API` ляжет напрямую в папку `API/`, при этом внутренние ссылки автоматически перепишутся на новые плоские пути; ветка `Руководство` останется иерархической.

### Типы трансформаций

| Тип | Описание |
|-----|----------|
| `remove_macro` | Удаление Confluence-макросов по имени (например, toc, status). Поддерживает `preserve_content: true` для сохранения содержимого |
| `remove_element` | Удаление HTML-элементов по CSS-селектору |
| `modify_links` | Замена URL в ссылках по правилам find/replace |
| `modify_content` | Замена текста в контенте (до или после конвертации) |
| `rewrite_tfs_links` | Перезапись ссылок TFS/Git-репозиториев на локальные пути |
| `rewrite_internal_links` | Перезапись внутренних ссылок Confluence на относительные пути |
| `expand_tiny_urls` | Раскрытие коротких ссылок Confluence (`/x/AbCd`) в полные URL перед перезаписью ссылок |

### Переопределение параметров через --set

Флаг `--set` позволяет переопределить параметры профиля без редактирования файла:

| Ключ | Описание |
|------|----------|
| `folder.naming` | Способ именования папок (slug, title, id) |
| `folder.length_limit` | Ограничение длины имён папок |
| `folder.flat_leaves` | Плоская структура для конечных страниц |
| `page.format` | Формат вывода контента |
| `page.strip_toc` | Удаление оглавления |
| `page.save_metadata` | Сохранение метаданных |

## Форматы контента

`confcli` поддерживает несколько форматов получения содержимого страниц:

| Формат | Флаг | Описание |
|--------|------|----------|
| Markdown | `--format markdown` | Конвертация из storage-формата в Markdown с поддержкой таблиц, панелей, макросов, блоков кода (по умолчанию) |
| Storage | `--format storage` | Сырой Confluence storage format (XML/HTML) — для последующего обновления страницы |
| Editor | `--format edit` | Формат редактора Confluence |
| Export | `--format export` | Export view, конвертированный в Markdown — чище для чтения, лучше для сложных таблиц |
| HTML | `--format html` | Сырой HTML |
| Plain | `--format plain` | Текст без HTML-тегов |

### Пример: получение в разных форматах

```bash
# Markdown (по умолчанию)
confcli page get --id 123456

# Storage — для редактирования и обратной загрузки
confcli page get --id 123456 --format storage

# Export — для документации и чтения
confcli page get --id 123456 --format export
```

## Форматы вывода

Глобальный флаг `--format` управляет форматом вывода метаданных:

```bash
# Текст (по умолчанию)
confcli page get --id 123456

# JSON (для автоматизации и парсинга)
confcli page get --id 123456 --format json

# YAML
confcli page get --id 123456 --format yaml
```

## Режим только для чтения

```bash
# Глобальный флаг
confcli --read-only page get --id 123456

# Или в конфигурации профиля
confcli config set read_only true
```

В этом режиме все операции записи (create, update, delete) будут отклонены.
